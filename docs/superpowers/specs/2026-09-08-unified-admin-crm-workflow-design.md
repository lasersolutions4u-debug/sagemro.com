## 当前有效范围：取代下方历史扩展方案

### 唯一优先目标

让海外客户的真实服务需求在现有系统中可靠走完：

**提交需求 → 商务报价 → 确认付款 → 派工/商务执行 → 服务报告 → 验收与售后。**

复用已有功能。先验证这条流程哪里确实不通，只修复阻碍它的具体问题，不为未来扩展提前重构。不以新增模块数量或建立完整组织体系作为验收标准。

### 仍须守住的业务规则

- 手工填写与 AI 协助复用现有请求表单，不再造入口。
- 工程师不对客户直接报价；确认适用启动款并正式派工前，不获得客户联系资料或任务通知。
- 无当地工程师时，保留商务在 Admin 实际服务及提交报告的已有路径。
- 保留现有报价、收款及开工审批安全门槛，不因功能收缩自动放权。
- 保留基础订单毛利估算；未配置分红规则不生成确定应付收益，不实施自动发薪。
- 参考物料成本和实际成本分清；库存、付款及审批不得重复记账。

## 1. 改造目标与边界

把现有平台整理为一套围绕客户、设备、工单和经营结果的管理系统：员工登录后，进入同一套业务页面，只能查看被授权的数据、执行被授权的操作。商务不再被隔离在重复的“商务工作台”里。

SAGEMRO 负责客户开发与跟进、报价和订单、设备服务、物料流转、业务审批、毛利及收益核算；企业微信负责日常办公、考勤请假、办公文档、采购报销和日常内部沟通。工单履约所需的物料采购动作仍留在 SAGEMRO；办公采购、费用报销及付款管理的边界见第 8 节。

采用“复用现有模块、逐批打通”的方案，不重新购买或搭建一套独立 CRM/OA，也不一次性重写后台。

| 备选方案 | 取舍 |
| --- | --- |
| 保留两套工作台，分别补功能 | 改动小，但重复页面、重复权限和重复录入会持续增加 |
| 一次合并页面、账号和国内国际数据库 | 表面统一，但数据迁移、权限和合规风险集中，不采用 |
| 分批统一页面与权限，保留数据边界 | 推荐；可以逐批验收、回退，不强迫合并数据库 |

“做完”的业务标准：商务能在同一套页面完成线索跟进、客户管理、建单、报价、付款跟进、履约跟踪和售后；工程师只收到满足付款及派工条件的服务任务；管理者能按授权审批、查毛利和配置收益规则。

## 4. 身份、市场、组织与权限

### 4.1 统一入口不等于合并数据

目标是一个管理体验、按授权可切换业务市场。界面语言、访问域名、浏览器 Origin 都不能代替服务器上的身份授权。

分两步实施：先让国内、国际现有后台使用同一套界面及权限规则；再在安全及合规核查后，实现一个入口下的身份映射/登录与市场切换。第一步不宣称已经实现单点登录。

当前 `worker/wrangler.toml` 将 `sagemro-db` 和 `sagemro-db-cn` 都绑定为 Cloudflare D1。代码区分 DB 与 DB_CN 说明逻辑隔离，不足以证明境内存储。国内前端的阿里云发布流程位于 `.github/workflows/aliyun-cn-deploy.yml`，前端在国内也不等于后端数据在国内。

P0 必须查清数据库实际位置、附件、备份、日志、AI 输入与检索、第三方处理及访问人员所在地区。若需要境内数据落地，将其作为单独基础设施迁移项目，另行制定备份、验证和回退方案；本方案不授权迁库。

境外远程查询境内个人信息可能涉及数据出境；不能因为统一后台、内部员工或超级管理员身份就自动豁免。参考[国家网信办数据出境问答（2025-10-31）](https://www.cac.gov.cn/2025-10/31/c_1763633376984070.htm)和[促进和规范数据跨境流动规定](https://www.cac.gov.cn/2024-03/22/c_1712776611775634.htm)。具体适用路径由实际数据流及专业合规评估确定，本方案不是合规认证。

技术边界：

- 身份映射不得按同名、同邮箱自动合并两地账号；不得直接共享或互信现有 JWT。
- 数据标识使用“市场 + 记录类型 + ID”，跨市场同 ID 不得串单。
- 切换市场须中止旧请求，清空旧列表、详情、选择项、弹窗及导出状态，重新获取授权。
- 服务端每次重新校验有效身份、市场、岗位能力、地域、上下级、记录归属和业务状态。隐藏按钮不构成授权。
- 权限变化需使过期页面操作、排队导出、审批任务和 AI 检索上下文失效或重新授权。
- 总部跨市场权限单独申请及配置；报表汇总不默认集中全部客户个人信息。

### 4.2 组织模型

建议内部结构：运营总监统筹采购/供应链、市场营销、商务；商务链为国家/区域商务总监 → 商务经理 → 商务专员，各岗位三档。

工程师合作组织独立：国家/大区总监 → 区域主管 → 工程师客服，各岗位三档。商务负责成交、客户关系和报价；工程师负责授权后的服务履约。

九档用于能力、绩效或收益规则，不等于同岗位高一档就能审批低一档；审批依据明确的直属上级关系。

现有商务总监模型不允许设置上级。接入运营总监审批前，必须扩展并验证组织约束，不直接往现有字段写入不符合规则的关系。

| 超级管理员 | 已合法配置的业务市场与范围 | 账号、组织、授权、审批及收益规则配置、审计 | 不绕过数据合规或历史结算审计 |
| 具名管理员 | 超管明确分配的市场与模块 | 指定业务管理、审批、收款确认等 | 不等同超级管理员；不自动管理根权限及薪酬 |
| 运营总监 | 授权市场及辖属组织 | 经营监督、流程管理、指定审批、服务标准监督 | 不默认全部基础设施权限或所有人的薪酬 |
| 商务总监 | 本人及辖属经理/专员，且在地域范围内 | 客户跟进、建单、报价、团队经营查看、下属知识审批 | 不自动获得最终报价审批、收款确认或派工权 |
| 商务经理 | 本人及直接下属专员 | 同类商务业务、下属知识审批 | 不看其他经理团队；不能自己审批自己的内容 |
| 商务专员 | 自己归属的业务 | 跟进、建单、报价、知识提交、服务评价查看 | 不查看平级业务，不管理组织或审批自己 |
| 采购/供应链 | 授权的物料及采购任务 | 采购记录、到货协同、相关申请处理 | 不自动查看所有客户、报价利润、工资 |
| 仓库 | 授权仓库及物料任务 | 备料、出入库、退料及盘点相关动作 | 不管理报价或商务收益 |
| 运营执行人员 | 已授予业务模块及范围 | 现有运营查看与物料审批等；按真实岗位细分 | 不因同属运营而获得总监能力 |
| 市场营销 | 授权渠道及线索 | 来源分析、线索录入及受控流转 | 不默认完整售后客户、订单成本或薪酬 |
| 工程师及其主管 | Engineer 中已派工任务、本人/辖属合作资料 | 履约、报告、物料申请、合作资料维护 | 不对客户直接报价；不自动登录 Admin |
| 客户 | 本人/获授权企业的记录 | 提交请求、确认报价、付款资料及服务验收 | 不看内部成本、毛利、分红及内部审批意见 |

知识和服务评价按业务归属收敛；物料参考目录则在获授权市场内共享，不按“谁创建物料”限制。员工工资、个人收益明细另设敏感权限，不能从“能管理团队业务”自动推导。

建议集中配置入口：系统设置 → 组织与权限 / 审批规则 / 绩效与分红规则。初期只有超级管理员可配置；具名管理员是否可以管理其中某部分另行授权。

## 5. 统一业务页面与 CRM

建议导航：我的待办、线索、客户、工单、物料、知识库、服务评价、经营分析、系统设置。按能力显示，不新增一个平行的商务专用业务系统。

“我的待办”是汇总入口；点开任务仍进入对应客户、工单或申请详情。旧商务工作台入口保留短期跳转，所有功能迁移及回归通过后再去除旧实现，不提前删除。

CRM 数据关系：客户企业 → 联系人/设备 → 线索及商机 → 报价/工单 → 履约与售后。保留现有客户登录身份，不将客户账号直接改造成企业主表；先核对现有设备和关联表，再决定是否新增企业、联系人或商机实体。

必须补齐：

- 线索覆盖维修、保养、升级改造、配件、新机和自动化方案。原“整机线索”保留为筛选条件。
- 来源记录真实来源，业务分类允许明确选择；不凭关键词把所有咨询自动判为新机采购。
- 销售阶段与工单状态分离。建议阶段为新线索、已联系、需求确认、报价中、协商中、成交、未成交；最终文案在对应界面设计中统一。
- 跟进记录包含负责人、记录时间、实际沟通内容、下一步及约定时间；到期提醒可处理/延期并留痕。
- “转客户/建商机/建工单”必须是明确动作，关联已有对象优先；改变线索状态不自动制造订单或收入。
- 商务可直接创建工单，不强制所有售后请求先经过商机；复用现有服务请求字段、校验及 AI 辅助资料，不造第二种表单。
- 同一客户详情串联设备、报价、服务、款项及售后历史，敏感字段仍按权限过滤。
- 相似联系人可提示人工核对，不跨市场自动去重或合并。
- 导出的是当前筛选下全部有权记录，不是当前页。导出字段、附件下载、导出次数/任务、操作人和授权版本可审计；处理 CSV 公式注入，不能将真实客户资料放入测试或日志。

## 6. 知识、服务评价、物料与工程师资料

### 6.1 知识库

直属上级审批：专员 → 经理 → 总监 → 获授权运营总监。运营总监未到位时，由超管作为明确兜底；无上级、上级离职或停用时进入可见异常待办，不静默通过。

允许本人及辖属内容查看、本人草稿编辑；批准后的修改产生新版本。内容提交、层级审批、技术安全审核、内部发布、用于 AI、公开发布是不同动作。

重要边界：

- 不允许作者自审；不能用商业层级审批替代高风险维修知识的技术审查和证据要求。
- 审批基于提交时内容快照；改内容后重新提交，不能批准未审阅的新内容。
- 缺少作者/归属的历史内容先由管理员分类，不凭创建日期或姓名猜归属。
- 公共设备手册与企业共享知识设置明确共享范围，不能因为“自己及下属”而使合法共享资料不可用。
- 内部批准不自动公开给客户或写入全局 AI 知识库；检索和附件也必须遵守内容范围与脱敏要求。

### 6.2 Service Reviews

统一中文名称为“服务评价”，与报告审核、开工审批分开。商务查看本人及辖属工单的客户评价，可另记内部跟进；不修改客户评分，不删差评，不扩大到全平台 AI 聊天反馈。

### 6.3 物料与工程师资料

商务可以查询授权市场内物料规格、参考销售价和报价所需参考成本。页面要区分参考成本、订单锁定成本及实际成本，并展示币种、税费口径、运费是否包含、来源和有效时间；缺少价格不按零计算。

保留工程师现有资料表，补齐商务候选人查询。建议资料包括：

- 小时/天人工费、最低计费、加班及在途计费、币种与报价有效期。
- 服务地点、覆盖范围、可出差地区、交通住宿标准、可接受差旅条件、可用时间与语言。
- 自有检测工具、维修设备、工作场地、辅助人员及远程支持条件。
- 激光器和切割头分别明确：诊断、换件、内部维修，以及支持品牌/型号、限制和证据。
- 服务经验及资质资料可提交验证；自报能力不等于平台已认证。

商务在报价阶段可以看符合范围的候选工程师能力和内部费用，但工程师不能因此看到该客户的资料或收到派工通知。此查询与正式派工是两个权限。

## 7. 报价、毛利、收益与结算

业务展示应明确四种不同结果：预计毛利、实际毛利、预计个人收益、已确认/已支付个人收益。

建议管理口径：

`预计毛利 = 同一税费口径的报价收入 − 预计配件成本 − 预计工程师服务成本 − 预计差旅成本 − 其他订单直接成本`

`实际毛利 = 按配置口径确认的实际收入 − 已核定直接成本`

`商务预计收益 = 满足适用条件的毛利基数 × 适用分配比例`

这些是管理展示框架，不代替会计、工资或税务制度。含税/不含税、收入确认与退款口径必须在正式结算启用前确定。同一订单不能混算币种，金额使用最小货币单位或现有受控精度方案。

规则要求：

- 商务使用毛利基础；合作工程师使用约定的收入基础。分别建规则，不把两种比例混为一谈。
- 工程师人工报价、工程师合作分红和订单实际支付需定义包含/替代关系，避免一笔工程师成本重复扣两次。
- 商务自身毛利提成不再次从其提成基数中循环扣除；管理口径与公司最终净利润分开。
- 未确定比例、基数或成本时显示“未配置/资料不完整”，不能展示虚构的收益或把未知成本算零。
- 超管配置岗位/职档默认规则和经批准的个人例外；个人例外优先于岗位档位，冲突必须显式提示。
- 规则有版本、生效区间、修改原因和审计。建议客户确认报价时锁定适用规则、参与人及报价版本；此前仅预估。
- 调整只影响以后满足条件的订单；历史订单不自动重算。退款、补成本、改归属通过关联原单的调整记录处理。
- 总监团队提成、多人分摊、亏损单、退款扣回、商务兼工程师是否可双重计酬，均须明确规则后启用，不能自行设百分比。
- 商务看自己的收益；管理者可看获授权团队经营毛利，查看他人个人工资/分红另需权限。
- 实际结算需核定收入、成本和必要审批。预计收益不是付款指令，本轮不实施真实发薪或自动支付。

## 8. 工单审批、物料与消息闭环

### 8.1 订单链路

服务请求 → 商务认领/归属 → 方案与成本估算 → 报价审批 → 客户确认报价 → 应付启动款确认 → 获授权人员派工 → 开工确认 → 服务及物料流转 → 报告/验收 → 成本和收益核定 → 结单及售后。

付款门槛对应已确认报价约定的启动条件，不擅自把所有项目改为必须一次性付清全款。金额、币种、报价版本不一致时不能推进。

商务归属不是实际派工。付款和报价条件未满足时，工程师不获得客户联系资料、服务任务及相关客户通知。条件满足后派给当地工程师；无合适工程师时，经授权由商务本人作为实际服务执行人，在 Admin 完成服务和报告。

首发仍由管理员承担当前最终报价审批、收款确认和实际派工门槛；以后超管可以按岗位/个人授予商务相应能力。调高职档或创建商务账号不自动放权。

### 8.2 审批中心

建立“我的待办”：待我审批、待我处理、我提交的、处理记录。复用现有报价、开工、物料、报告等业务状态；待办只是索引，批准动作必须回到原业务校验。

首版采用有限的现有业务类型和可配置审批人，不做可执行任意脚本的通用流程设计器。配置涵盖适用事项、审批岗位/直属上级、备用审批人及必要金额阈值。新增会改变既有业务门槛的规则必须单独验证。

每次审批验证操作者最新权限、原单版本、付款状态及审批对象。重复点击/重复回调幂等；两人并发处理时仅一方成功，另一方得到已处理或版本冲突提示。审批失败不发送成功通知。

### 8.3 物料申请

复用申请、提交、审核、备料/缺货采购、到货、出库、工程师确认、退料和关闭。审批通过、库存变化、采购支付是不同事件，不能一次批准就假设全部完成。

关联工单、数量、仓库、成本来源与处理记录；防止重复领料、重复预留和超量。物料消耗及退料影响订单成本，但不直接重写已结算历史。

与企业微信边界：SAGEMRO 记录工单所需物料、履约采购及订单成本；企业微信处理公司采购付款/报销等办公流程。若人工录入同一笔外部费用，保留外部单号并核对，防止重复计入成本。未来是否打通需独立确认，当前不自动同步。

### 8.4 消息系统

现有收件箱复用会话能力；审批待办单独关联业务事件，不能仅凭“读了消息”就完成审批。

权限必须同时限制收件人、会话参与人、附件、消息预览和推送内容。对工程师的客户信息通知只能在付款及派工门槛满足后产生。改派、离职、停用及时撤销后续访问，历史审计仍保留。

业务状态提交与通知事件采用可靠的一致性机制；重试不重复发真实邮件、消息或创建任务。企业微信通知如以后接入，优先最小化单号和鉴权链接，不默认发送客户、报价、利润或工资详情。

## 9. 实施路线与首批开工边界

每批先本地测试，再确认 PR/上线范围；超过五个文件修改前单独展示文件和影响范围。不得用一次总体方案确认替代生产操作确认。

| 阶段 | 范围及主要现有落点 | 完成标准/依赖 |
| --- | --- | --- |
| P0 基线与数据边界 | 现有组织/权限、部署文件及数据流清单 | 明确已有功能与缺口；境内存储及跨境访问不能含糊。生产读取另行确认 |
| P1 统一授权基础 | `businessIdentity.js`、`businessWorkspace.js`、认证路由、员工账号 | 先抽取可复用范围规则；逐项补能力授权、组织变更失效和审计；业务权限不扩大 |
| P2 统一业务入口 | `App.jsx`、客户/线索/工单页、现有商务报价/执行组件 | 商务用共享页面；范围覆盖列表、详情、导出和写入；直接建单及原流程通过回归 |
| P3 业务知识与报价资料 | 知识、评价、物料、工程师资料 | 直属审批+技术审核分离；商务获范围内查询；不暴露客户给候选工程师 |
| P4 CRM 闭环 | 现有客户/设备/线索表与接口 | 企业与联系人关联、跟进/商机、全类型线索、转换幂等及完整导出 |
| P5 工单待办与授权审批 | 收件箱、报价执行、物料、服务报告模块 | 一个待办入口；付款后派工、商务执行和通知门槛完整；不重复业务账 |
| P6 经营核算与组织扩展 | 毛利估算、规则配置、工程师合作资料 | 版本化规则、收益快照、核定与调整；工程师九档、本地仓申请及新增岗位按独立子批次实施 |

单入口登录/跨市场切换作为 P1/P2 的独立子批次：必须先完成 P0 数据流与身份方案评审。未过关时，先统一两地界面和功能，不合并登录或自动开放跨市场。

首个工程批次仅涉及四个后端文件：抽取现有已验证的商务上下级范围规则、补测试、接入原查询。它是后续共享页面的基础，首批本身不产生新菜单、不放权、不迁库。详细操作见配套第一批计划。

后续 P2–P6 是可验收路线，不冒充已经写好每一行实现；每个阶段开工前补该阶段精确文件、迁移和测试计划，避免同时改账号、审批、库存和财务。

## 10. 测试、发布与回退门槛

- 权限矩阵测试：本人、下属、平级、跨团队、跨地域、跨市场、无归属、停用上级、调岗和无效会话；同时验证列表/详情/附件/搜索/导出/AI，而非只测菜单。
- 业务链测试：报价版本变化、缺成本、支付不足、错误币种、重复确认、提前派工、撤销/改派、商务自行履约及报告提交。
- 审批测试：自审拒绝、无上级/停用上级、版本冲突、审批后改内容、消息失败重试、库存并发及重复回调。
- 核算测试：未知成本、退款、负毛利、多币种、规则切换、多人分配、改归属、退料；未配置规则不得算出“确定可支付”。
- 全部使用虚构客户和内存/本地数据，不发送真实消息，不生成真实订单或支付。
- 沿用项目现有完整 test job，包括 Worker、前端检查/测试/构建、Admin 构建及适用浏览器回归；不能只凭计划内单元示例宣称可上线。
- 新增数据迁移先在本地验证；编号以实际最新分支为准，不在本方案预占。生产迁移须确认目标库、备份可恢复及影响，人工执行，CI 不替代迁移。
- 国内、国际分支分别验证。实际发布依据 `.github/workflows/deploy.yml` 和 `.github/workflows/aliyun-cn-deploy.yml`；不能照抄旧 AGENTS 的部署描述。
- 发布前二次确认目标域名/组件、版本、数据库变更、备份及回退。兼容式迁移优先；回退应用前检查 schema 兼容，不通过直接删列/删数据“回退”。
- 生产健康异常、数据异常立即停止并告知，不继续尝试修补或推进后一批。

## 11. 历史需求保留为回归基线

以下方向来自前期确认，当前改造不重做网站，亦不把未经本轮验证的功能宣称为全部已上线：

- `.com/.cn` 为品牌及服务入口；公共工具/洞察归品牌站，AI 页保持简洁，不重新加 Tools、Insights、Engineer Portal 或“关于”入口。
- 服务请求表单是核心入口；手工填写和 AI 对话协助最终进入同一工单链路，不重复建表单。
- 不公开服务电话/WhatsApp；公开支持邮箱 `support@sagemro.com`，客户自己的联系方式可包含电话及 WhatsApp。
- 国内手机号、国际邮箱身份确认保留其适用规则，界面语言不替代验证方式和市场身份。
- 维修、保养、升级、拆装搬迁、配件及已确认可受理的其他项目按实际能力呈现；尚无成熟方案的业务先评估，不承诺确定交付。
- 国内全国可协调，国际按所在地及项目评估；价格按地区、设备和项目透明报价，不虚构统一时效、质保或收费条件。
- 品牌覆盖和 SEO 文案以实际可服务能力为依据，不堆砌或暗示官方授权；官网和系统使用一致 Logo/色调，避免无依据“已审核”日期。
- 英文 Store 链接保留用户指定的 DHgate 店铺；中文商城未准备好时不放误导性购买入口。

## 12. 待确认事项与安全默认

本方案已将用户确定的方向整理为可执行约束。以下不是要求马上逐项回答，而是在相应批次正式启用前必须解决的业务选择。

| 事项 | 建议/安全默认 | 确认时点 |
| --- | --- | --- |
| 单一后台最终域名、SSO 及数据位置 | 先保留现有入口；不跨库合账号、不推断境内落地 | P0 后、单入口子批次前 |
| 运营总监未任命时的审批链 | 超管作为明确兜底，禁止自审，异常不静默通过 | P3 审批启用前 |
| 新内部岗位权限 | 独立最小能力模板，默认不启用；超管配置后生效 | P1/P6 对应子批次 |
| 商务最终审批/收款确认/派工 | 首发维持管理员门槛，人员到位后明确授予 | P5 放权前 |
| 收益比例、税费/收入口径、双重计酬、团队分配 | 未配置不计作应付，不虚构百分比；负毛利如实显示 | P6 核算启用前 |
| 收益规则锁定时点 | 建议客户确认报价时锁定，后续通过调整单处理 | P6 设计确认时 |
| 本地仓投资条件 | 先记录申请，不自动生成投资承诺、合同或分红 | P6 本地仓子批次 |
| 企业微信接口 | 先采用办公流程分工；系统接入另行确认 | 用户明确需要接入时 |

审阅本方案后，建议从 P1-A 范围规则复用及回归测试开工；随后完成能力授权，再迁移业务页面。不要从“先把所有菜单开放”开始。
