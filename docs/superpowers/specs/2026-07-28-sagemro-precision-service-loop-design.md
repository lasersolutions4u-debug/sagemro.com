# SAGEMRO 精准服务闭环设计

> 状态：已确认
> 日期：2026-07-28
> 适用范围：`sagemro.com`、`sagemro.cn`、客户工单、工程师工作台、Admin
> 设计目标：把现有通用检查清单升级为可传播、可执行、可验证的 SAGEMRO 品牌服务体系。

## 1. 背景

现有工程师工单页包含六条静态“服务标准检查清单”，但存在四个问题：

1. 六项内容混合了服务前、服务中和服务后动作，工程师不容易判断当前重点。
2. 勾选状态只存在于当前页面，不构成可审计的服务记录。
3. 清单缺少品牌命名、阶段结构、强制门禁和客户价值表达。
4. 右侧 AI 仅提供服务前核查，不能在完整服务周期内持续指导工程师。

SAGEMRO 的产品定位是官方标准化服务体系，而不是开放工程师撮合平台。本设计将固定服务规范、确定性质量门禁、AI 动态指导和客户可见证明组合成一套完整服务闭环。

## 2. 目标与成功标准

### 2.1 目标

- 建立一套中英文一致、可对外传播的 SAGEMRO 六步服务标准。
- 在工程师工单页持续提醒当前阶段、必做事项和下一步动作。
- 对安全、付款、现场证据、恢复测试和服务报告实施可审计的关键门禁。
- 让客户在选择前理解 SAGEMRO 的优势，在服务中看到品牌承诺正在兑现。
- 复用现有 AI 服务前核查的缓存、证据指纹、并发租约、隐私和失败降级机制。

### 2.2 成功标准

- 工程师在任意工单标签页都能识别当前六步阶段。
- 工程师进入下一关键阶段前，系统能明确指出未完成的强制事项。
- AI 每次最多突出三个下一步动作，并能生成可编辑的客户确认消息。
- AI 不可用时，固定清单、进度、门禁和工单主流程仍可正常工作。
- 客户看到的完成状态全部来自工程师、Admin、客户确认或系统业务事件，不来自 AI 推测。
- 中英文站点使用同一规则和数据，只使用不同文案。

### 2.3 非目标

- 不让 AI 自动完成清单、自动批准安全条件或自动推进工单。
- 不把内部风险推理、付款提醒、内部备注或受保护现场证据展示给客户。
- 不在本次设计中建立设备品牌或机型专属的完整维修 SOP 库。
- 不用数量庞大的配置系统替代第一版统一六步标准。

## 3. 品牌框架

### 3.1 名称与品牌承诺

中文名称：

**SAGEMRO 精准服务闭环 · 六步法**

英文名称：

**SAGEMRO Precision Service Loop**

中文承诺：

**每一次服务，都有准备、有依据、有验证、有交付。**

英文承诺：

**Every service is prepared, evidence-based, verified, and clearly delivered.**

### 3.2 六步标准

| 步骤 | 中文名称与客户价值 | 英文名称 | 固定标准 |
| --- | --- | --- | --- |
| 1 | **任务对齐**：到场前，把问题说清楚 | **Task Alignment** | 确认设备身份、故障现象、生产影响、客户目标、联系人和服务时间。 |
| 2 | **风险锁定**：动手前，把风险控住 | **Risk Control** | 识别适用风险，确认停机、隔离、防护、现场许可和责任人。 |
| 3 | **一次备齐**：出发前，把资源准备充分 | **One-Visit Readiness** | 核对人员、工具、仪表、备件、耗材、资料、软件、现场条件及适用的付款前置条件。 |
| 4 | **循证执行**：服务中，每一步都有依据 | **Evidence-Based Execution** | 先记录现象和基准，再诊断和处理；保存操作、参数、配件和前后变化，范围变化需先授权。 |
| 5 | **恢复验证**：交付前，用结果证明恢复 | **Recovery Verification** | 按约定工况验证功能、质量与安全保护，完成现场复原并记录遗留风险。 |
| 6 | **透明交付**：完工后，让服务形成闭环 | **Transparent Handover** | 提交现象、根因、措施、配件、测试和建议完整的服务报告，并建立客户确认和后续跟进。 |

六步名称和顺序固定，不由 AI 生成。AI 只能为每一步补充当前工单特有的子项、风险和建议。

## 4. 角色与可见范围

### 4.1 工程师

- 查看完整六步标准、所有适用事项、内部门禁和 AI 指导。
- 确认本人负责的清单事项。
- 对 AI 建议进行采纳、忽略或纠正。
- 将 AI 生成的客户问题作为草稿带入消息，发送前必须人工确认。
- 对“不适用”事项填写原因。

### 4.2 区域负责人和 Admin

- 查看完整进度、异常、确认人、证据引用和审计记录。
- 对授权范围内的事项确认或退回。
- Admin 可以人工覆盖门禁，但必须填写原因并写入审计日志。
- 区域负责人不能替代执行工程师确认只有现场执行人才能确认的事实。

### 4.3 客户

- 查看六步公开里程碑、已验证的完成状态和需要客户配合的事项。
- 不查看内部风险推理、付款内部跟进、工程师工作笔记、受保护证据或 AI 原始输出。
- 对需要客户确认的事项执行明确操作，例如补充信息、确认服务时间、确认测试结果或确认报告。

## 5. 客户侧品牌触点

### 5.1 `sagemro.com` / `sagemro.cn` AI 开始页

放置位置：现有 AI 介绍区域下方、公开资源区域上方。

展示一个精炼的“为什么选择 SAGEMRO”模块：

1. **更早发现风险**：AI 整理事实，专业人员确认边界。
2. **更充分地准备**：减少信息缺失和不必要的重复上门。
3. **每一步有证据**：诊断、处理和验证过程可追溯。
4. **让服务形成资产**：报告进入持续关联的设备服务档案。

模块提供“了解六步服务标准”入口，打开 About 中的完整说明。

### 5.2 关于 SAGEMRO

现有 About 内容保留 AI 能力边界、设备记录和长期价值说明，并新增完整的“精准服务闭环”章节：

- 品牌承诺；
- 六步名称、客户价值和执行标准；
- AI 与人工确认的职责边界；
- 服务记录如何沉淀；
- 哪些内部信息不会向客户公开。

About 是完整说明书，但不是唯一入口。

### 5.3 客户工单详情

放置位置：工单状态摘要下方、工单标签页或详情内容上方。

客户看到：

- 六步里程碑和当前阶段；
- 已完成的公开事实；
- 当前 SAGEMRO 正在处理的事项；
- 客户需要配合的下一步；
- 最终报告、验证结果和后续建议入口。

客户不看到 AI 的内部建议，只看到经过规则验证后形成的公开进度。

## 6. 工程师工单页布局

### 6.1 桌面端

使用三个层级：

1. **全局六步进度条**
   放在工单摘要下方、标签页上方。无论工程师切换到消息、报价、物料、现场服务或服务报告，都能看到当前阶段。

2. **当前阶段任务清单**
   替换概览页现有的通用六项平铺清单。默认只展开当前步骤；已完成和未来步骤可以折叠查看。

3. **右侧 AI 服务指导**
   升级现有 AI 服务前核查卡，放在右侧栏最上方、Admin 支持上方，并在桌面端保持粘性定位。

### 6.2 手机端

信息顺序：

1. 工单摘要；
2. 六步进度；
3. AI 当前提醒；
4. 标签页内容。

AI 卡默认只显示一句“当前最重要”和阻塞数量，点击后展开建议、依据和客户问题草稿。

## 7. 六个阶段门

六步进度独立于现有工单状态保存。工单状态提供允许范围，清单与业务事件决定阶段是否完成。

| 阶段门 | 进入下一阶段前的基线条件 |
| --- | --- |
| 任务对齐 → 风险锁定 | 设备身份、问题、目标、联系人、服务方式和时间窗已确认。 |
| 风险锁定 → 一次备齐 | 适用风险、隔离条件、现场许可、PPE 和责任人已确认。 |
| 一次备齐 → 循证执行 | 必需工具、资料和关键资源已确认；适用的开工前付款条件已满足；Admin 已批准开工。 |
| 循证执行 → 恢复验证 | 上门签到或远程开始条件有效；基准证据、服务动作、配件/参数变化和范围授权记录完整。 |
| 恢复验证 → 透明交付 | 功能、质量、安全保护和现场复原结果已记录；遗留风险已明确。 |
| 透明交付 → 完成 | 服务报告完整；客户确认路径、后续建议和必要的交付资料已建立。 |

规则要求：

- 强制事项必须为 `confirmed` 或有权人员确认的 `not_applicable`。
- 选择 `not_applicable` 必须填写原因，并记录操作人和时间。
- AI 发现缺口可以创建建议，但不能改变事项状态。
- Admin 覆盖门禁必须有原因和审计日志。
- 远程、上门和混合服务可以拥有不同的适用事项，但共享同一六步外层结构。

## 8. AI 实时服务指导

### 8.1 AI 输出

右侧 AI 每次只输出工程师当前可执行的信息：

- 当前步骤；
- 一句“当前最重要”；
- 风险或信息缺口；
- 最多三个下一步动作；
- 最多两个可编辑的客户确认问题；
- 需要补充的证据；
- 建议依据的来源类别；
- 结果生成时间和是否已过期。

AI 不输出隐藏推理过程，不承诺已查看未实际分析的图片或视频。

### 8.2 输入证据

允许输入：

- 工单结构化字段和脱敏描述；
- 设备品牌、型号及允许的设备档案；
- 客户与工程师之间的公开工单消息；
- 允许的客户 AI 对话摘要；
- 附件和受保护媒体的数量及人工审阅状态；
- 报价、付款、物料、现场作业和服务报告的结构化状态；
- 六步清单当前状态。

禁止输入：

- 客户或工程师原始联系方式；
- 内部备注；
- 受保护现场媒体 URL 或未经允许的原始媒体；
- 隐藏系统提示；
- 无界 JSON 或未经限制的自由文本。

### 8.3 刷新触发

以下事件立即重新计算确定性进度，并将 AI 指导标记为过期：

- 工单状态、派工、服务方式或服务时间变化；
- 客户或工程师新增公开消息、附件或设备信息；
- 报价、付款或物料状态变化；
- 现场签到、作业记录、证据计数或范围授权变化；
- 恢复测试、服务报告或客户确认变化；
- 工程师纠正 AI 建议。

AI 采用近实时后台刷新：

- 相同证据指纹不重复调用模型；
- 连续事件合并处理；
- 同一工单同一时刻只允许一个生成租约；
- 旧建议在新结果生成前继续可见，并显示“信息已更新”；
- 通常数秒内替换，超时后停止轮询并提供重试。

AI 指导允许在 `assigned` 至 `pending_review` 的完整活动服务周期内生成。`completed` 工单只读最后一份已保存结果，不再触发新生成。由此避免服务已经开始但右侧指导卡因没有历史结果而完全消失。

### 8.4 与现有实现的关系

保留现有 `work_order_service_readiness` 的物理表和安全机制，避免对已上线迁移进行破坏性重命名。将其概念升级为生命周期服务指导缓存：

- 保留 `input_fingerprint`、`generation_state`、生成租约、旧结果保留和错误状态；
- 增加当前步骤、指导版本和触发原因；
- 将现有服务前核查 JSON 作为版本 1 兼容数据；
- 新版本输出严格校验的生命周期指导 JSON；
- 前端逐步从旧 `/service-readiness` 接口切换到 `/service-guidance`，兼容期内旧接口继续可读。

## 9. 数据模型

第一版六步定义保存在服务端版本化常量中，不提供 Admin 自定义编辑器。步骤和事项使用稳定 key；中英文界面按 key 映射文案。任何会改变门禁含义的调整必须提升 `standard_version`，避免旧工单被新规则静默改写。

### 9.1 六步进度

新增 `work_order_service_standard_progress`，每个工单的每个标准事项一行：

| 字段 | 用途 |
| --- | --- |
| `work_order_id` | 工单 |
| `standard_version` | 六步标准版本 |
| `step_key` | 六步阶段 |
| `item_key` | 稳定事项标识 |
| `state` | `pending` / `confirmed` / `not_applicable` / `legacy_not_recorded` |
| `is_required` | 是否构成门禁 |
| `confirmed_by_type` / `confirmed_by_id` | 确认主体 |
| `confirmed_at` | 确认时间 |
| `evidence_type` / `evidence_id` | 可选证据引用 |
| `not_applicable_reason` | 不适用原因 |
| `updated_at` | 最近更新时间 |

复合唯一键：`work_order_id + standard_version + item_key`。

`blocked` 是根据未完成强制事项派生的门禁结果，不单独存为事项状态。`legacy_not_recorded` 仅用于兼容旧工单，不能被计为已经验证完成。

### 9.2 AI 指导缓存

在现有服务前核查缓存基础上增加：

- `guidance_version`；
- `current_step_key`；
- `trigger_reason`；
- 严格校验的 `guidance_json`。

AI 缓存不是服务事实来源，也不作为客户里程碑完成依据。

### 9.3 审计

以下动作必须写入现有审计体系：

- 强制事项确认；
- 将强制事项标记为不适用；
- Admin 门禁覆盖；
- 阶段推进或退回；
- 工程师纠正 AI 建议。

## 10. API 边界

建议提供以下职责清晰的接口：

- `GET /api/workorders/:id/service-standard`
  返回六步定义、事项状态、当前步骤、门禁和角色可见数据。

- `POST /api/workorders/:id/service-standard/items/:itemKey/confirm`
  确认事项或标记不适用；服务端校验角色、状态和必填原因。

- `GET /api/workorders/:id/service-guidance`
  只读缓存，不触发同步模型调用。

- `POST /api/workorders/:id/service-guidance/refresh`
  非阻塞刷新，复用证据指纹和生成租约。

- 客户工单详情接口返回独立的 `public_service_milestones`，不把内部标准对象发送给客户后再依赖前端隐藏。

## 11. 失败、并发与降级

- AI 调用失败：保留上一份有效建议；没有旧建议时显示失败与重试，不隐藏固定六步标准。
- AI 超时：沿用生成租约过期机制，防止永久 `generating`。
- 并发刷新：条件更新抢占租约；迟到任务不能覆盖新结果。
- 工单并发推进：门禁校验和状态更新必须以数据库当前状态为准，失败时返回冲突并重新加载。
- 证据被删除或权限变化：重新计算指纹并停止引用失效证据。
- 页面刷新或切换标签：从服务端读取持久化进度，不使用浏览器本地勾选状态作为事实来源。

## 12. 旧工单兼容

- 新建工单从六步第一阶段开始完整记录。
- 已完成历史工单不反向生成“已验证”事项，避免虚假证明。
- 服务中的旧工单根据当前业务状态初始化当前阶段，但过去步骤标记为 `legacy_not_recorded`，客户只看到“已进入当前服务阶段”，不显示未经记录的逐项完成证明。
- 已有服务前核查结果继续可读，并在下一次有效刷新后升级为新指导格式。

## 13. 测试策略

### 13.1 单元测试

- 六步阶段与适用事项计算；
- 远程、上门、混合服务门禁差异；
- 强制事项、不适用原因和 Admin 覆盖；
- AI 输入脱敏、限长、证据指纹和输出校验；
- 客户公开里程碑不能包含内部字段。

### 13.2 API 测试

- 工程师、区域负责人、Admin、客户权限矩阵；
- 非执行工程师不能确认现场事项；
- 门禁未满足时不能推进关键状态；
- 并发确认、并发刷新和生成租约；
- AI 失败、超时、无配置和预算耗尽降级。

### 13.3 前端测试

- 桌面端三个位置和手机端顺序；
- 当前阶段展开、其他阶段折叠；
- 强制项、普通提醒、阻塞原因和不适用原因交互；
- AI `ready`、`stale`、`generating`、`failed` 状态；
- 中英文文案和长文本布局。

### 13.4 端到端测试

至少覆盖：

1. 一张远程服务工单从任务对齐到客户确认；
2. 一张上门服务工单经过安全门禁、签到、现场证据、恢复验证和报告；
3. 客户补充信息后 AI 指导标记过期并后台更新；
4. AI 故障时工程师仍能按固定标准完成合规流程；
5. 客户端从首页品牌承诺进入 About，并在工单中看到相同六步里程碑。

## 14. 上线顺序

1. 建立六步定义、进度数据、门禁和审计，不改变 AI。
2. 升级工程师页面的全局进度条和当前阶段清单。
3. 将右侧 AI 服务前核查升级为全生命周期服务指导。
4. 在客户工单中增加公开里程碑。
