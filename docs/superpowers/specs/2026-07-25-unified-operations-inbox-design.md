# 统一运营收件箱设计

**状态：** 已确认，待实施

**日期：** 2026-07-25
**范围：** Admin 与工程师端；客户端不新增收件箱

## 目标

为运营人员、区域负责人和工程师提供一个统一收件箱，集中处理：

1. 与工单关联的协作会话；
2. 不关联工单的双向私信；
3. 现有系统通知与待处理事项。

客户保留现有工单消息入口，不进入统一收件箱，也不可见任何内部私信或内部消息。

## 角色与权限

权限必须由 Worker 校验，前端仅按后端返回的可用联系人和会话展示操作。

| 发起方 | 可私信对象 |
| --- | --- |
| Admin（运营 Joe） | 所有工程师与所有区域负责人 |
| 区域负责人 | 运营 Joe 与直属下属工程师 |
| 工程师 | 运营 Joe 与自己的区域负责人 |

- 普通工程师不能相互发起私信。
- 区域负责人与其下属的关系以 `engineers.regional_lead_id` 为准。
- 会话成员均可回复已加入的私信会话；发送消息前再次校验成员关系与账号状态。
- Admin 账号不作为 `engineers` 记录存放；一期将其表示为当前受认证的 admin 用户。界面显示名称为“运营 Joe”。

## 数据模型

新建迁移（下一序号），不扩展 `work_order_messages`。

### `inbox_conversations`

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `kind` | `direct` / `work_order` / `system` |
| `work_order_id` | 可空；工单会话的关联工单 |
| `subject` | 可空；私信主题或系统通知标题 |
| `created_by_id`, `created_by_type` | 创建者身份 |
| `last_message_at` | 收件箱排序字段 |
| `created_at`, `archived_at` | 生命周期字段 |

为 `kind, last_message_at` 及 `work_order_id` 建索引。一个工单默认只有一个内部协作会话；用唯一索引或创建逻辑确保不重复。

### `inbox_participants`

| 字段 | 说明 |
| --- | --- |
| `conversation_id` | 会话 |
| `user_id`, `user_type` | 参与人；`admin` / `engineer` |
| `last_read_message_id` | 未读边界 |
| `joined_at`, `left_at` | 成员状态 |

联合唯一键为 `(conversation_id, user_id, user_type)`；按 `(user_id, user_type, left_at)` 建索引。

### `inbox_messages`

| 字段 | 说明 |
| --- | --- |
| `id`, `conversation_id` | 标识与归属 |
| `sender_id`, `sender_type`, `sender_name` | 发件人快照 |
| `content` | 文本内容，沿用服务端长度与净化约束 |
| `attachment_urls` | 预留 JSON；一期 UI 不提供上传控件 |
| `created_at`, `edited_at` | 时间字段 |

按 `(conversation_id, created_at)` 建索引。消息不可在一期删除或编辑，保留协作审计记录。

系统通知不迁入这三张表：继续写入既有 `notifications`，收件箱通过聚合 API 显示它们，并保留既有已读行为。

## API

所有接口位于 `/api/inbox`，统一使用现有认证中间件。

| 接口 | 行为 |
| --- | --- |
| `GET /api/inbox` | 返回按最近活动排序的会话、未读数及系统通知摘要；支持 `filter=all|action|required|work_order|direct|system` |
| `GET /api/inbox/contacts` | 返回当前用户有权私信的联系人；不返回无权限对象 |
| `POST /api/inbox/conversations` | 创建或复用一对一私信；后端校验发起人与目标的权限矩阵 |
| `GET /api/inbox/conversations/:id` | 返回会话、参与人、分页消息及关联工单摘要；校验参与者身份 |
| `POST /api/inbox/conversations/:id/messages` | 发送消息，更新 `last_message_at`，并创建收件人站内通知 |
| `POST /api/inbox/conversations/:id/read` | 推进当前参与人的 `last_read_message_id` |
| `POST /api/inbox/work-orders/:workOrderId` | 仅有权访问该工单的内部身份创建或获取对应内部协作会话 |

`GET /api/inbox` 的未读计数应合并私信/工单内部会话未读和既有 `notifications` 未读；但分别返回计数，以便 UI 清楚区分。

工单 API 保持兼容。工单详情增加“内部协作”入口，跳转至此工单的 `work_order` 会话；不把内部 `inbox_messages` 返回给客户工单消息接口。

## UI 与交互

### Admin

- 在侧栏新增“收件箱”，带总未读徽标。
- 三栏布局：筛选与新建私信、会话列表/消息、会话与工单上下文。
- “新建私信”联系人为全部工程师与区域负责人；显示姓名和角色。
- 工单详情保留现有客户可见消息与内部备注，并添加“打开内部协作”快捷入口。

### Engineer / 区域负责人

- 工程师工作台增加收件箱入口与未读徽标。
- 联系人列表严格按 API 返回。区域负责人可看到直属团队成员；工程师只看到“运营 Joe”和自己的区域负责人。
- 工单详情中的内部协作入口只显示给 admin、区域负责人和工单工程师；客户端不显示。

### 会话状态

- 收件箱会话行显示来源（工单/私信/系统）、最近消息、时间、未读标记。
- 打开会话后立即提交已读状态；发送方看到“已送达”，一期不做逐人已读回执。
- 系统通知沿用现有弹窗的“标记已读”语义，并可跳转工单或收件箱会话。

## 提醒策略

- 所有新私信及重要工单协作消息创建站内未读记录。
- 国际站工程师端在已有 OneSignal 可用且用户已订阅时，推送关键消息和派工；普通消息仅站内提醒，以免骚扰。
- Admin 一期无离线浏览器推送，仅站内未读与轮询。
- `.cn` 域名继续不调用 OneSignal；站内未读和轮询是完整可用的降级路径。
- 不接入短信、微信或其他外部即时通信渠道。

## 安全与边界

- 任何联系人查询、建会话、读会话、发消息和标记已读均在 Worker 重新验证身份与关系。
- 不以 URL 中传入的 `user_id` 决定权限；以认证身份为准。
- 不允许客户访问 `/api/inbox`；收到请求返回 403。
- 内部私信和工单内部协作消息绝不写入 `work_order_messages` 的客户可见通道。
- 复用现有文本长度限制；附件表结构预留但一期不启用，以控制范围。

## 测试与验收

Worker 测试应覆盖：

1. 权限矩阵的允许与拒绝组合，尤其是普通工程师互发、跨团队区域负责人发起、客户访问；
2. `regional_lead_id` 更新后联系人权限立即变化；
3. 一对一会话重复创建时复用原会话；
4. 非成员无法读取、发送或标记会话；
5. 会话未读数、站内通知和读取状态正确变化；
6. 工单内部协作会话与客户可见工单消息严格隔离；
7. 通知发送失败不影响消息持久化。

前端测试应覆盖：

1. admin 与工程师端入口、未读徽标和筛选；
2. 后端联系人集对应的“新建私信”可见性；
3. 从工单详情进入关联会话；
4. 客户端不渲染收件箱或内部协作入口；
5. `.cn` 域名不尝试初始化 OneSignal。

## 非目标

- 客户统一收件箱、客户私信；
- 工程师间任意私信；
- 群聊、公告编辑、消息撤回/编辑、文件上传；
- WebSocket 实时连接；一期以请求后刷新和轮询实现；
- 短信、微信等第三方通知渠道。

## 部署说明

此功能新增 D1 migration。部署 Worker 前必须按项目部署规范，分别在生产数据库执行该 migration 并验证 `_migrations` 记录；否则新 API 会因表不存在而失败。中国版 Worker 使用独立 D1 数据库，也需同步迁移。
