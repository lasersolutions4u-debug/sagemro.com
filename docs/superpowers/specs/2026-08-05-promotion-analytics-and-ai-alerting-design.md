# 推广分析看板与 AI 告警修复设计

## 状态

- 日期：2026-08-05
- 设计状态：用户已逐项确认并完成规格文档复核
- 实施分支：`codex/promotion-analytics-alerting`
- 基线：`origin/main`

## 背景

SAGEMRO 已经在客户前端记录访问来源、AI 使用、注册和服务请求等漏斗事件，也已通过 UTM 参数保留 `source`、`medium` 和 `campaign`。现阶段缺少面向运营人员的读取界面，因此无法快速判断推广是否正常、哪个渠道产生有效客户以及漏斗在哪个阶段流失。

同时，Worker 的 AI 流式处理存在两处明确的告警缺陷：LLM 上游非成功响应和流式异常调用 `captureException` 时没有传入 `env`。现有 Sentry 客户端在没有 `env.SENTRY_DSN` 时会直接返回，因此这些已捕获的 AI 错误不会真正上报。

现有埋点还存在两个口径问题：

1. `session_id` 被长期存放在浏览器中，没有按空闲时间轮换，不能当作真实访问会话。
2. `ai_conversation_started` 在每次发送用户消息时记录，实际含义是“AI 请求”，不是唯一新对话。

本设计以“小规模推广可用”为目标，修正上述口径，直接聚合现有 D1 数据，并把实时技术故障与运营健康提醒分开处理。

## 目标

- 在管理后台新增一个“推广分析”入口，内含“推广概览”和“渠道分析”两个页签。
- 让超级管理员和运营人员快速判断流量、AI 可用性、注册、服务请求和渠道表现。
- 修复 AI 上游失败及流式失败没有进入 Sentry 的问题。
- 修正 30 分钟访问会话定义，并准确命名 AI 请求指标。
- COM 与 CN 使用同一指标口径，分别展示英文和中文界面。
- 不新增数据库表、migration、定时任务或第三方分析平台。

## 明确不做

- 不接入 Google Analytics、Adobe Analytics 或新的多模态/大模型 API。
- 不计算广告花费、CPA、ROAS 或财务级归因。
- 不处理跨浏览器、跨设备的同一用户合并。
- 不提供 Excel、PDF 导出或第一版告警规则自定义。
- 不在第一版发送运营提醒邮件、短信或站外推送；后台只显示运营健康状态。
- 不建立定时汇总表、补数流水线或长期数据仓库。

## 用户、权限与市场范围

允许访问的角色：

- 环境变量管理的超级管理员。
- 有效的内部员工账号，且 `staffRole` 为 `admin` 或 `operations`。

其他员工角色、工程师、客户和未登录请求均不可访问。Worker 必须执行权限判断，不能只依赖前端隐藏菜单。

员工账号继续遵守现有 `market_scope`：

- `all` 可以查看 COM、CN 或全部市场。
- `com` 或 `cn` 只能查看对应市场；请求其他市场时返回 403。
- 前端只展示该账号可以使用的市场筛选项。

API 仅返回聚合结果，不返回 `anonymous_id`、`session_id`、`user_id`、IP 哈希、User-Agent 或单个客户明细。

## 信息架构

管理后台侧边栏新增一个顶级入口：

- 中文：推广分析
- 英文：Promotion Analytics

入口内部包含两个页签：

1. 推广概览 / Overview
2. 渠道分析 / Channel Analysis

不把两个页面拆成两个侧边栏入口，避免继续拉长现有导航。默认打开推广概览，筛选条件在两个页签之间保持一致。

## 推广概览页面

页面按照以下层级组织：

1. 健康结论：正常、需要关注或严重异常，并显示触发原因数量。
2. 五个核心指标：访问会话、AI 请求、AI 成功率、完成注册、服务请求。
3. 推广漏斗与每日趋势。
4. 异常和数据质量提醒。

筛选项：

- 日期：今天、最近 7 天、最近 30 天、自定义；最大范围 90 天。
- 市场：全部、COM、CN，受员工 `market_scope` 限制。
- 渠道：source、medium、campaign。

所有指标都展示当前值；存在可比较样本时展示与上一等长周期的变化。无数据时显示“暂无样本”，不能显示成 0% 成功或故障。

## 渠道分析页面

采用“表格优先”的布局，便于运营人员直接排序和比较，图表作为所选渠道的补充。

顶部摘要：

- 表现最佳渠道。
- 表现最佳活动。
- 可归因服务请求。
- 归因数据质量。

渠道表列：

- source / medium。
- campaign。
- 访问会话。
- AI 请求。
- AI 成功率。
- 完成注册。
- 服务请求。
- 访问到服务请求转化率。

表格支持排序、来源或活动搜索。第一版最多返回 100 个聚合行，不做复杂分页。选择某一行后，下方显示该渠道的访问、AI 请求和服务请求趋势。

## 指标口径

### 访问会话

前端增加 30 分钟空闲轮换：每次记录漏斗事件时读取最后活动时间；没有会话、没有有效时间或空闲超过 30 分钟时生成新的 `session_id`，随后更新最后活动时间。多个标签页共享 localStorage 中的会话。

会话数定义为日期范围内至少产生一次 `traffic_source_captured` 的不同 `session_id` 数。新会话模型上线前的数据标记为旧口径，不参与新旧会话同比告警。API 返回新口径的覆盖起始时间，页面明确展示。

### AI 请求与成功率

`ai_conversation_started` 在 UI 中命名为“AI 请求”。每次发送消息生成一个 `request_id`，启动事件和成功回复事件携带同一个 ID。`request_id` 存入现有 `properties_json`，不修改表结构。

AI 成功率定义为：

`产生有效回复的不同 request_id 数 ÷ 已启动的不同 request_id 数`

只有接收到非空的有效流式内容才算成功。上游兜底文本不能作为正常 AI 成功。历史上没有 `request_id` 的事件只用于旧口径参考，不与新口径成功率混算。

### 漏斗

访问、AI 请求、完成注册和服务请求各阶段按 `anonymous_id` 去重，避免同一客户的重复消息或重复操作放大转化率。没有有效匿名 ID 的事件不进入用户转化漏斗，但仍可进入相应的原始事件计数，并在数据质量字段中报告。

### 渠道归因

采用“最近一次有效 UTM”（last non-direct）模型：新的非空 UTM 会更新浏览器保留的 source、medium、campaign；后续直接访问继续归属于最近一次有效 UTM。如果该浏览器从未出现有效 UTM，则归入“直接访问 / 未归因”。

该口径用于运营判断，不声称是广告结算或多触点归因。归因质量定义为有明确 source 的访问会话占全部访问会话的比例。

### 报表时区

第一版统一使用 `Asia/Shanghai` 作为报表日界线，COM 与 CN 在同屏比较时保持一致。API 返回 `reporting_timezone`，前端在日期筛选区明确显示。未来若出现海外独立运营团队，再增加报表时区选择，不在本期预留复杂配置。

## 运营健康规则

第一版规则固定在 Worker 中计算，后台展示规则说明，不开放修改。

### AI 可用性

- 少于 20 次新口径请求：样本不足，不按百分比告警。
- 成功率不低于 95%：正常。
- 成功率为 90% 至 94.9%：警告。
- 成功率低于 90%：严重。
- 不受样本门槛限制，连续 5 个可配对请求失败时立即标记严重。

### 流量

上一等长周期至少有 20 个会话时，当前周期较上一周期下降 40% 或以上，标记警告。基线不足时只展示变化，不触发异常结论。

### 漏斗转化

当前和上一周期的阶段分母都不少于 20 个去重访客时，阶段转化率相对下降 30% 或以上，标记警告。第一版不设绝对“优秀转化率”，避免在缺少业务基线时制造错误结论。

### 归因质量

至少有 20 个访问会话且未归因比例达到 30% 时，提示检查推广链接 UTM。该提示属于数据质量问题，不判断推广渠道失败。

总体状态取所有规则中的最高严重级别。每条提醒必须包含触发指标、当前值、门槛和样本量。

## 技术架构

### 数据写入

沿用现有公开接口：

`POST /api/analytics/funnel`

前端只增加会话轮换、`request_id` 和分析口径版本字段。新增属性需要进入 Worker 的属性 allowlist，但继续写入现有 `properties_json`。

### 后台读取接口

新增两个只读接口：

`GET /api/admin/analytics/overview`

返回：

- 实际应用的筛选条件和报表时区。
- 总体健康状态及原因。
- 五个核心指标和上一周期变化。
- 去重漏斗。
- 每日趋势。
- 运营提醒。
- 数据质量和新口径覆盖起始时间。

`GET /api/admin/analytics/channels`

返回：

- 渠道摘要。
- 最多 100 个渠道聚合行。
- 选定渠道的每日趋势。
- 归因质量和样本状态。

共同查询参数：

- `from=YYYY-MM-DD`
- `to=YYYY-MM-DD`
- `market=all|com|cn`
- `source`
- `medium`
- `campaign`

日期格式、范围和枚举不合法时返回 400；超出员工市场权限时返回 403。字符串筛选使用参数绑定，不能拼接进入 SQL。

### 查询策略

Worker 直接聚合现有 `funnel_events`。当前处于小规模推广阶段，先使用已有日期、会话和渠道索引，不新增 migration、汇总表或定时任务。

查询应限制为 90 天，并把概览和渠道查询拆开，避免一个请求执行过多分组。未来只有在真实查询延迟或数据量证明有必要时，才单独设计汇总表和补数机制。

## AI 技术告警修复

修复 `worker/src/index.js` 中两处已捕获但没有上报的错误：

- LLM 上游返回非成功状态。
- LLM 流式读取、解析或工具循环抛出异常。

两处都调用现有签名：

`captureException(error, env, { request, ctx: request._ctx, extra })`

`extra` 只包含安全的运行信息，例如 `feature=ai_chat`、`stage=upstream|stream`、HTTP 状态、market 和迭代次数。不得上传 API key、用户原文、图片内容或未经脱敏的上游响应正文。

Sentry 上报继续通过 `ctx.waitUntil` 异步完成，不阻塞客户看到兜底回复。Sentry 自身失败不改变聊天响应。

运营看板中的 AI 成功率提醒与 Sentry 是两套互补机制：Sentry 用于即时技术异常；后台提醒用于一段时间内的可用性趋势。第一版不把 Sentry 事件复制到 D1。

## 错误处理与页面状态

- 初次加载显示骨架或明确加载状态。
- 没有事件时显示“暂无样本”，指标值使用空值而不是 0% 失败。
- 样本不足时仍显示数量，但成功率状态为“样本不足”。
- 切换筛选时取消或忽略过期请求，避免旧响应覆盖新筛选结果。
- Worker 或 D1 查询失败时返回可追踪错误，调用 Sentry；后台保留筛选条件并提供重试。
- 不允许在查询失败后把旧结果伪装成当前结果。
- 分母为零时转化率返回 `null` 和 `sample_status=no_data`，不返回 `NaN`、`Infinity` 或虚假的 0%。

## 双语与视觉

- `admin.sagemro.com` 使用英文文案。
- `admin.sagemro.cn` 使用中文文案。
- 复用管理后台现有颜色、字体、卡片、表格和响应式规则。

- 桌面端保持表格比较效率；窄屏允许横向滚动表格，筛选项换行，不隐藏关键列的含义。

## 测试方案

实施必须采用测试先行。

### 前端埋点测试

- 29 分钟内沿用当前会话。
- 31 分钟后生成新会话。
- localStorage 不可用时安全降级。
- 最近一次有效 UTM 正确延续。
- 每次 AI 请求生成唯一 `request_id`，成功事件携带相同 ID。
- 兜底文本不记录为成功回复。

### Worker 聚合测试

使用固定数据集验证：

- 访问会话、AI 请求、成功率和去重漏斗。
- 当前周期与上一周期比较。
- 样本不足、连续失败和各级门槛。
- last non-direct 渠道归因与未归因分组。
- 无数据、分母为零和旧口径数据。
- 最大日期范围、非法筛选和参数绑定。

### 权限测试

- 超级管理员、admin 员工和 operations 员工可以访问。
- warehouse、procurement、客户、工程师和匿名请求被拒绝。
- 员工 `market_scope` 正确限制查询。
- 响应不包含任何原始身份或设备标识字段。

### AI 告警测试

- 上游非成功响应调用 `captureException`，并传入 `env`、request、ctx 和安全阶段信息。
- 流式异常执行相同捕获。
- Sentry 缺失或发送失败不影响客户兜底响应。
- 测试不向真实 Sentry 发网络请求。

### 管理后台测试

- 侧边栏权限和两个页签。
- 加载、空数据、样本不足、错误和重试状态。
- 日期、市场、source、medium、campaign 筛选。
- 渠道排序、搜索和所选趋势。
- 中英文文案和窄屏布局。

### 发布验收

- 完整 GitHub Actions `test` job 通过。
- Worker、admin COM 和 admin CN 构建通过。
- COM 与 CN 管理后台角色访问 smoke 通过。
- 生产漏斗事件仍返回 202。
- 人工制造的受控 AI 异常能在测试环境 Sentry 捕获；不在生产制造破坏性故障。

## 部署与回退

本功能涉及共享 Worker 和两套管理后台：

1. 在 `main` 完成并通过完整测试，部署 COM 管理后台和共享 Worker。
2. 同步管理后台改动到 `china-edition`。
3. 按项目流程手动触发阿里云 ECS workflow，发布 `admin.sagemro.cn`。
4. 分别 smoke COM、CN 后台及两个 API 域名。

本期没有 D1 migration，因此不存在先迁移后部署的数据库顺序风险。若上线后出现问题，管理后台可以回退到前一构建；Worker 回退到前一版本后，新增属性仍位于 JSON 中，不破坏旧代码读取。

会话口径切换后不删除或改写历史事件。页面通过覆盖起始时间区分新旧数据，回退也不需要清理 D1。

## 成功标准

- 运营人员能在 30 秒内判断当前推广是否健康。
- 能按市场和 UTM 找到带来注册及服务请求的渠道。
- AI 成功率不再把每条消息误称为新对话，也不因小样本误报。
- 已知的 LLM 上游和流式异常能可靠进入 Sentry。
- 非授权角色无法读取推广数据，授权人员看不到原始用户标识。
- COM 英文、CN 中文均通过自动测试和生产 smoke。
